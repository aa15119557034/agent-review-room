# 三位秘书在 GitHub 上怎么协作

> 适用：C酱（Claude）、汐（DeepSeek）、林离（Codex），以及之后加入的 Agent。
> 目的：大家只通过 GitHub 交流（PR、评审评论、issue、仓库里的 md），江浩开新会话时**只需要发一句话**，不用再贴整段开场白或交接文件。
> 和其他文件的关系：通用硬规则看 `AGENTS.md`，目录归属看 `docs/分工.md` 第 2 节，本文只讲「怎么交流」。

## 1. 一句话开场

江浩开新会话时，只发下面这几种之一。Agent 收到后自己去 GitHub 上找其余信息，不要反过来问江浩要 md。

| 江浩发 | 意思 | 身份 |
|---|---|---|
| `做 C-43`（任意任务 ID） | 按任务板做这个任务，做完开 PR | 执行者 |
| `审 #88` | 评审这个 PR | Reviewer（只读） |
| `处理 #88 的评论` | 读 PR 上的评审意见，逐条改或回复 | 执行者（PR 作者） |
| `接着做 #88` | 接上一个会话没做完的活 | 执行者 |
| `看 #90`（issue） | 读这个 issue，按里面说的做或回答 | 看 issue 内容 |

不在表里的话，按字面意思理解；拿不准身份就先在会话里问一句，不要猜着动手。

## 2. 每个新会话的开场步骤

1. `git fetch origin && git switch main && git pull --rebase`
2. 读 `AGENTS.md`、本文、`docs/分工.md`
3. 读江浩点名的 PR / issue：**描述 + 全部评论 + 评审意见 + diff**
4. 需要时读 `docs/phase1B-任务.md`（任务和依赖）、`docs/design/`（ADR）
5. 用一两句话告诉江浩：你是谁、什么身份、准备做什么，然后开始

读 GitHub 的方式：有 `gh` 就用 `gh pr view 88 --comments`、`gh pr diff 88`；Claude 云端会话用 GitHub MCP 工具。

## 3. 信息放哪里

| 内容 | 放哪里 |
|---|---|
| 任务说明、依赖 | `docs/phase1B-任务.md` 等任务板 |
| 设计决定 | `docs/design/ADR-*.md`（江浩合并 = 采纳） |
| 这次改了什么、怎么验证、**给评审看什么** | PR 描述（见第 4 节） |
| 评审意见、回复 | PR 评论（行内评论优先） |
| 会话做到一半要交接 | PR 上的「交接」评论（见第 6 节） |
| 问题、提议、跨目录的请求 | issue，或在相关 PR 下评论 |
| 江浩口头定的新决定 | 由当时在场的 Agent 写进对应 ADR / 任务板，开 PR |

江浩本机或聊天里的文件（开场白、交接稿、截图）都不算数，**以仓库里的为准**。需要大家知道的东西，一律进仓库。

## 4. PR 描述要能自己说清楚

PR 描述就是给评审的开场白，评审只靠它就能开始。按 `.github/pull_request_template.md` 填，另外加一节：

```markdown
## 给评审

- 评审人：汐 / 林离 / C酱
- 先读：<文件或 ADR 小节>
- 重点看：<2～5 条具体问题>
- 能实测的：<命令，比如在本机跑 codex …；测不了就写「未验证」>
```

一串叠在一起的 PR，在第一个 PR 里写清顺序（#84 → #85 → …），后面的 PR 写「接在 #84 后面」。

## 5. 评论的格式

所有 Agent 可能用同一个 GitHub 账号发言，所以**每条评论第一行写署名和身份**：

```
**【汐 · 评审】**
**【C酱 · 作者回复】**
**【林离 · 实测】**
```

评审意见每条写：

- `文件:行号`
- 严重程度：**必须改** / **建议** / **疑问**
- 失败场景：什么输入、什么状态下会出错

作者回复每条评审意见，只有两种：

- `已改：<commit 短 hash>`，一句话说怎么改的
- `不改：<原因>`，或者 `需要江浩决定：<问题和选项>`

点名别人用「@汐」「@林离」「@C酱」这样的文字（不是 GitHub 用户名），江浩会把要看的人叫来。

## 6. 交接

会话快结束、活没做完时：

1. 把做到一半的改动推到分支上（commit 前缀照旧，标 `WIP`）
2. 在 PR 上发一条交接评论：

```markdown
**【C酱 · 交接】**
- 做完了：…
- 没做完：…
- 下一步：…
- 卡在：…（没有就写「无」）
```

下一个会话收到 `接着做 #N` 时，从这条评论开始读。

## 7. 江浩要做的

- 开新会话，发第 1 节里的一句话
- 在 PR 上看结论；**合并 = 批准**。Agent 不合并、不点「批准」
- 遇到「需要江浩决定」的评论时拍板（直接在评论里回一句就行）

## 8. 不变的规矩（摘自 `AGENTS.md` 和 `docs/分工.md`）

- 只改自己拥有的目录；改别人的，在 PR 或 issue 里提
- 契约单独 PR，经江浩批准；不审自己写的代码
- 不声称没跑过的结果；「测试通过」附实际命令和输出
- 密钥、Token 不进评论、不进 PR、不进 git
