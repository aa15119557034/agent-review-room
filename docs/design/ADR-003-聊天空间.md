# ADR-003：聊天空间（聊天 + 讨论室待办，手机端的主板块）

- 状态：**提议中**（等用户批准）
- 日期：2026-10-23
- 提出：Claude ｜ 评审：DeepSeek、Codex ｜ 批准：用户
- 关联：ADR-002（讨论室）、`docs/phase1B-任务.md`

## 背景

1A 的讨论室已验收（`docs/Phase1A-验收记录.md`）。讨论室是「正式评审」：每次发送都盖章、按轮推进、产出方案版本。

用户还要一块**更日常的空间**，并且以后在手机上它是**首要的大板块**（2026-10-23 用户原话整理）：

- **聊天部分**：能访问各自的记忆存储和完整人设，像人一样发散地聊；单聊、群聊都要
- **工作部分**：和讨论室联通，做成类似 GPT / Claude 远程模式那样（在别处看进度、发指令），但要简化
- 聊得好的内容可以**一键转成议题**，进讨论室正式评审

这超出 ADR-002 的范围（ADR-002 里手机端只做盖章、通知、议题只读），按规则先写 ADR。

## 决定

### 1. 两个部分，一条分界线

| | 聊天 | 工作 |
|---|---|---|
| 是什么 | 单聊 / 群聊，发散地聊 | 讨论室和（1C 起）执行任务的**简化遥控面板** |
| 盖章 | **不盖章**，打字就发 | 凡是会改变结果的动作（发一轮、汇总、定稿、合并）**照旧盖章** |
| 人设 | **完整人设**（每个 Agent 单独一份「聊天人设」，可以很长） | 用讨论室的三句角色设定 |
| 能动什么 | **只能说话**：不改文件、不跑命令、不联网写入 | 由讨论室 / 执行阶段的规则决定 |

分界线：**聊天里说的话，永远不会直接变成动作。** 要变成动作，只能「转成议题」，进讨论室走盖章流程。这样聊天不盖章也不会降低安全底线。

### 2. 聊天部分

- **会话**：单聊（你 + 一位）或群聊（你 + 任选几位）。会话列表按最近活跃排序
- **谁回答**（2026-10-23 修订，用户决定；判定规则按汐、林离评审补全）：
  - 单聊：对方总是回答
  - 群聊里 **@所有人** 或 **@某人**：被点到的人**必须回答**
  - 群聊里**没点名**：每位成员自己判断要不要回答
  - **点没点名只看结构化数据**：发送时在 @ 选择框里选中的成员 id 或 `all`，随消息一起存。正文里打的「@汐」、引用、语音转写、附件里出现的 @ 都**不改变**收件人规则
  - 没点名时仍给每位成员一个 Run，模型必须给出可解析的 `reply` 或 `skip`：**只有明确的 `skip`** 才记「不回答」（Run 正常结束、不建回复消息）；空输出、解析失败、超时、额度缺席各走各的状态。单聊或被点名的人给出 `skip` 按失败处理，不能悄悄显示成「不回答」
  - 聊天回答位用**自己的结局集合**（C-34 定义 `ChatSlotOutcome`：已答 / 不回答 / 额度缺席 / 失败 / 已取消 / 已撤回），**不改讨论室的 TurnOutcome**，0-B 不受影响。界面和导出分别显示「失败」「额度缺席」「这条没有回」；「不回答」不算缺席
  - 注意成本：判断「要不要回」本身也要调用一次模型。先按「每人一个 Run、可以选择不回答」实现；如果额度吃紧，再考虑由 C酱 一个人先判断谁来回（另提）
  - **Agent 之间不会自己接着聊**（没有自动多轮，和 ADR-002 一样），避免停不下来、费额度
- **@ 的输入方式**：在输入框里打 @ 就弹出成员选择（所有人 / 每一位），不在输入栏上放固定的 @ 按钮
- **消息类型**（2026-10-23 用户要求）：
  - **文字**
  - **语音**：录音存原文件（16k 单声道），同时转成文字；发给 Agent 的是**转写文字**（Agent 听不到声音）。转写在主控机本地做，不上传到第三方，转写结果可以先改再发。C-34 先定字段（音频引用、转写文字、语言、时长、状态、模型版本）；工具选型由汐用 10 段真实录音实测后决定（候选：sherpa-onnx + Paraformer、whisper.cpp），以独立进程运行。原始音频和转写都在备份 / 导出范围内
  - **表情包**：你自己的表情库，**1B 只支持静态表情**（png / jpeg / webp，不支持 GIF 动图，用户 2026-10-23 决定）；发给 Agent 时附带一句文字说明（例如「[表情：小鲸鱼比心]」）；1B 里 Agent 只发文字，不发表情
  - **文件和图片**：存在主控机上（和头像同一套引用规则，C-32），按内容去重；1B 只做「存储 + 引用 + 文本 / 图片进 Prompt」，PDF / Word 解析和 OCR 放到 1C。文本类文件按附件规则进不可信边界；图片只发给这一次所用模型能看图的收件人（2026-10-23 改：「能看图」看模型不看人，由节点在模型列表上实测上报，见 ADR-004 §2），其他人收到「[图片：文件名]」
- **撤回和重新编辑**（2026-10-23 用户决定；实现细节按汐、林离评审补全）：
  - 只能撤回**自己的**消息，**5 分钟内**（按主控机时间算，界面倒计时只是显示）
  - 撤回后时间线显示「你撤回了一条消息 · 重新编辑」；**「重新编辑」在撤回后 5 分钟内可用**（用户决定）
  - **原文仍然保存**在数据库里（消息详情里能看到），但**撤回之后新建的任何 Prompt / Run 都不再带它**。已经发出去的内容（不可变的 Snapshot、模型已经看到的）收不回来，这一点如实说明
  - 撤回后，以下内容都从之后的上下文里排除：原消息、针对它的已答回复、**包含它们的历史摘要**（摘要记录来源消息 id；受影响的摘要标为过期，下次发送前重建）
  - 撤回时：先落库（消息标撤回、回答位标已撤回、发出取消请求），再中止正在答的 Run（结局 `cancelled`）；撤回瞬间刚好答完的结果按「迟到结果」丢掉，不会把回答位改回已答，每个 Run 仍然恰好一个终止事件。撤回后的旧 Snapshot 不能被「重试」重新发出
  - **重新编辑 = 一条新消息**：新的消息 id、新的回答位（同样的 @ 规则），用 `replacesMessageId` 指向原消息、显示在原来的位置，带「已重新编辑」标记；旧回答位和旧 Run 归档保留，不删除，也不会因为防重复逻辑被当成重发
  - 已撤回的消息不能被选进「转成议题」
  - 秘书们的消息不能撤回；讨论室里的记录照旧不可撤回、不可修改
- **一次发送 = 一组回答位**（汐评审意见）：你发的一条消息，对每个收件人有一个「回答位」，唯一键是「用户消息 id + Agent」。所有回答位和 Run **在同一个事务里建出来**；某人不可用（节点不通、暂停、额度缺席）时，他的回答位直接记为缺席，**其他人照常回答**（聊天风险小，不像讨论室那样整条失败）。界面按回答位显示「汐回答中 / 林离已答 / C酱失败」，失败的可以**单独重试**，不会重发给别人
- **防重复**：用户消息 id 由发送方生成，同一个 id 重复发送只算一次（网络重试不会重复回答、重复计费）
- **硬上限**（后端强制，不只靠界面提醒）：一条消息最多 8 个收件人；每个会话每分钟最多 6 条
- **重启**：聊天的 Run 和讨论室一样进入「中断修复」，应用被强杀后重启，不会留下一直转圈的回答
- **人设**：`AgentProfile` 新增「聊天人设」（长文本，上限另定），和讨论室的三句 `roleNote` 分开。汐的锚点、林离的完整设定放在这里
- **记忆**：每个 Agent 可以配置一个「记忆来源」，回答前把相关记忆放进上下文：
  - **节点上的记忆文件夹**：比如你的 V0.4.1 分层记忆文件，放在 Agent 所在电脑上，由节点读取，内容不经过主控端以外的地方
  - **本聊天空间的历史**：之前的聊天记录（按会话，最近的全文、更早的摘要，和讨论室的压缩方式一样）
  - **做不到的**：claude.ai、ChatGPT、DeepSeek 网页里的云端记忆，命令行调用读不到，也不去读本机登录凭据绕过（ADR-002 已定）。界面上如实显示「此记忆来源不可用」
- **写记忆**：1B 只读。Agent 想记住什么，只能在回答里提议，由你决定是否写进记忆文件夹（以后再做「一键记下」）
- **可信 / 不可信，逐项列清**（林离评审意见）：
  - 可信指令区只有两样：**用户配置的聊天人设**、**当前这条经过发送者校验的用户消息**
  - 其余一律是带 nonce 的资料：历史里的旧消息（包括江浩自己的旧消息）、所有 Agent 发言、**历史摘要**（系统生成的也一样，不升级成指令）、记忆正文及其文件名 / 来源标记、附件、转议题时选中的消息
- **记忆正文的数据流**（林离评审意见，选定如下）：
  1. 主控端拼好除记忆以外的全部内容，生成不可变的 Snapshot（照旧落库、算 hash），Snapshot 里只留一个**记忆槽位**：写明「来源 X，由节点填入」和本次的 nonce
  2. 节点读自己的记忆文件夹，用**和主控端同一个包裹函数**（从 core 导出）把记忆放进槽位的 nonce 边界里，再发给 Agent
  3. 节点回报**记忆清单**：用到了哪几条（条目 id + 每条 sha256）和**最终实际发出内容的 sha256**。主控端只存清单和 hash，**不存记忆正文**
  4. 所以：Snapshot 的 hash = 主控端拼的部分；最终 hash = 实际发出的全文，由节点计算；两者都记在 Run 上。聊天不盖章，最终 hash 用于事后核对，不用于批准
  5. 每位 Agent 的记忆只进自己的 Prompt（记忆文件夹按节点 profile 配置，别人的 profile 读不到）；导出聊天记录时不含记忆正文

### 2a. 记忆文件夹怎么放（2026-10-25 修订）

江浩 2026-10-25 决定：记忆文件夹不由他给路径，三位秘书自己建、自己安排；要给以后的「强记忆」插件和「世界」板块留位置。本节替换任务板第 0 步里「告诉 Claude 记忆文件夹在哪」那一条。

**本节不改契约**：`MemorySource`、`MemorySlot`、`MemoryManifest`、`NodeHealth.memoryProfiles` 都按 C-34 已合并的样子用；下面是节点配置和文件夹约定（S-20 实现，归 `apps/agent-server/`）。主控端要跟着改的配置和一键导入单列成 C-44 / D-40（见「主控机拆成两个节点」）。

#### 放在哪台电脑、哪个位置

| 秘书 | 电脑 | 位置 |
|---|---|---|
| C酱 | 江浩的电脑 | `<AgentRoom>\memory\claude\` |
| 汐 | 主控机 | `<AgentRoom>\memory\deepseek\` |
| 林离 | 主控机 | `<AgentRoom>\memory\codex\` |

- 一台电脑上只有在这台电脑上的秘书的文件夹，别人的不建
- `<AgentRoom>` 是这套软件在每台电脑上的「家」，**每台电脑各自定，不一定在 C 盘**（江浩 2026-10-25）：S-20 的安装脚本在这台电脑上选好位置（比如 `D:\AgentRoom`），写进这台电脑节点配置的 `homeDir`。两台电脑的位置可以不同
- **`<AgentRoom>` 必须在本机 NTFS 盘上**：安装脚本和节点启动时都检查，FAT / exFAT、网络盘、可移动盘一律拒绝（这些盘上权限不生效）
- 不放进仓库、不放进任何用户目录（低权限账号不该能读用户目录）
- 布局：

```
<AgentRoom>\
  node\              节点程序和每位秘书的节点配置、Token（见「权限」）
  memory\<秘书>\     记忆（下面）
  plugins\           以后的插件（现在不建）
  world\             以后的世界板块（现在不建）
```

#### 每位秘书的记忆文件夹

```
<AgentRoom>\memory\<秘书>\
  memory.json        设置
  README.md          给人看的说明，节点不读
  core\              身份、和江浩的关系、长期约定：每次都带，一条都不能少
  notes\             长期笔记，可以有子文件夹；旧记忆原样放这里（例如汐的 V0.4.1 分层记忆放 notes\v0.4.1\）
  journal\           经历和日记：journal\YYYY\MM-DD.md 或 journal\YYYY\MM-DD-<别的>.md（两种都在年份文件夹下）
  inbox\             以后「一键记下」先写到这里，江浩确认后再挪进 notes；1B 节点不读
  ext\               以后强记忆插件的私有数据，每个插件一个子文件夹；1B 节点不读
```

`memory.json`：`{ "version": 1, "budgetChars": 20000, "maxFileBytes": 65536 }`

- `budgetChars`：1,000～50,000；按 **Unicode 码点**数（不是 UTF-16 单元，也不是字节）
- `maxFileBytes`：4,096～1,048,576
- 文件缺失、JSON 坏了、多了或少了字段、`version` 不认识、数值越界 → 整个来源 `unavailable`，节点日志写原因。不夹紧、不用默认值顶上（悄悄换值会让人以为设置生效了）

#### 1B 节点怎么挑记忆（内置的「文件夹」读法）

1B 没有按话题检索，规则固定，同一份文件在哪台电脑上挑出来都一样。

**哪些文件算候选**

1. 只看 `core\`、`notes\`、`journal\` 下的 `.md` / `.txt`；`inbox\`、`ext\`、`README.md`、`memory.json` 不看
2. 不是 `.md` / `.txt` 的文件直接忽略（不算问题，`.gitkeep` 这类也一样）。候选里跳过（记 warning）：名字以 `.` 开头的（Windows 的「隐藏」属性不看：记忆正文只有江浩能写，隐藏属性挡不住也放不进什么）；超过 `maxFileBytes`；不是合法 UTF-8；条目 id 不合 `MemoryEntryId`（比如相对路径超过 200 字符）；`journal\` 里文件名不合上面格式的
3. **不跟随符号链接、junction 和任何重解析点**；规范化后的真实路径不在这位秘书的文件夹里就跳过
4. **硬链接数大于 1 的文件跳过**（硬链接不是重解析点，挡不住；正常记忆文件不会有第二个链接）

**顺序**

- 排序键里的路径一律用条目 id（相对路径，`/` 分隔）按 Unicode 码点逐个比较：区分大小写，不看区域设置
- `core\`：按 id
- `journal\`：按路径里的日期（`YYYY` + `MM-DD`）新的在前，同一天按 id；**不看修改时间**
- `notes\`：按修改时间新的在前，修改时间相同按 id。修改时间会被复制改掉，所以搬电脑时用保留时间的方式复制（S-20 的脚本用 `robocopy /COPY:DAT`），README 里写明

**怎么截断**

1. **先放 core**：core 是「每次都带」，不截断。`core\` 不存在或一个候选文件都没有、core 里任何一个文件被第 2～4 条跳过、或者 core 合计超过 `budgetChars`、或者 core 超过 200 个文件 → **整个来源 `unavailable`**，日志写原因。不带残缺的身份
2. 再按顺序放 journal，然后 notes：**放得下就放，放不下就跳过这一条、继续看下一条**（后面更短的可能放得下）；总条数到 200（契约上限）就停
3. 字数 = 每条正文的码点数之和（不算包裹边界的固定文字）

**结果**

- 条目 id = 相对路径（如 `core/identity.md`）；回报的 sha256 是这条正文的 hash
- 文件夹不存在或读不了、`memory.json` 无效、core 不合格 → `unavailable`；都合格但挑不出条目 → `empty`
- 节点启动时按同样的规则检查一遍，不合格的 profile 不进 `memoryProfiles`，界面显示「此记忆来源不可用」

#### 节点配置（S-20）

节点配置顶层加 `homeDir`（这台电脑的 `<AgentRoom>`，绝对路径）和 `runAsUser`（见下）。只有聊天 profile 能配记忆，讨论 profile 配了就启动报错：

```json
"claude-chat": {
  "memory": { "dir": "memory/claude", "provider": "folder" }
}
```

- `memory.dir` **只能是 `memory/<agent>`**（`agent` 见下面「权限」），不能写绝对路径，不能有 `..`；启动时再查一次真实路径就是 `homeDir\memory\<agent>\`，不对就启动报错并写明原因（配置错误，不当成「不可用」）
- `provider` 1B 只有 `folder`（上面的读法）。以后的强记忆插件在这里换成插件 id，见下

#### 权限：一位秘书一个低权限账号

**主控机上汐和林离各跑一个节点进程，各用各的账号**（`agentroom-deepseek`、`agentroom-codex`），江浩的电脑上是 `agentroom-claude`。原因：林离的讨论 profile 能读文件（`codex --sandbox read-only` 能读整个硬盘），和汐共用账号就能读到汐的记忆。分开账号后，「别人的读不到」由系统权限保证，不靠节点代码。

**节点怎么以这个账号运行**

- 用 Windows 计划任务：开机启动、「不管用户是否登录都运行」、运行身份是 `agentroom-<秘书>`。不从江浩自己的会话里直接启动
- 节点启动时检查当前进程的用户是不是配置里的 `runAsUser`，不是就拒绝启动（防止误用江浩的账号跑起来，那样权限全都不起作用）
- 节点配置顶层加 `agent`（`claude` / `deepseek` / `codex`）：所有 profile id 必须以 `<agent>-` 开头，否则拒绝启动。一个节点账号下只会跑这一位秘书的命令行
- 节点程序放 `<AgentRoom>\node\app\`：各节点账号只读
- 每位秘书的节点配置和 Token 放 `<AgentRoom>\node\<秘书>\`：这位秘书的账号和管理员能读；别的秘书账号、插件账号都没有权限
- **隔离的对象是「秘书之间」，不是「秘书和她自己的节点」**（汐复审疑问）：林离的讨论 profile（`codex --sandbox read-only`）在 `agentroom-codex` 下能读到她自己节点的配置、Token 和命令行登录信息。这些拿到了也只能以林离的身份调林离自己的节点，不扩大权限，所以不再拆账号。聊天 profile 没有工具，读不了文件
- **主控机上的 Token 文件另外给江浩的账号只读**（林离复审意见）：桌面端的 main 以江浩的普通账号运行（不提权），一键导入（C-44 / D-40）要能读到 `node\deepseek\agent-server.token` 和 `node\codex\agent-server.token`。只给这两个文件，不给整个文件夹；不依赖管理员组。C酱的节点在江浩的电脑上，Token 照旧在界面里粘贴
- 命令行的登录信息（Claude、Codex 的 `CODEX_HOME`）在这个账号自己的用户目录里，S-20 的脚本带着在这个账号下登录一次

**记忆文件夹的权限**（`<AgentRoom>` 关掉继承：很多盘的根目录默认给「已验证用户」建文件夹和修改的权限）

| 谁 | `core` `notes` `journal` | `inbox` | `ext\<插件 id>` |
|---|---|---|---|
| 江浩的账号、管理员 | 完全控制 | 完全控制 | 完全控制 |
| 这位秘书的节点账号 | 只读 | 无（1B 不读） | 无 |
| 这个插件的账号（以后） | 只读 | 无 | 读写（只有自己的） |
| 其他所有账号 | 无 | 无 | 无 |

节点账号和插件账号对记忆正文都**没有写权限**，所以没法在记忆文件夹里放链接把别的文件「伪装」成记忆；第 3、4 条是第二道门。

**主控机拆成两个节点**（汐、林离评审意见）

现在主控端的推荐配置里汐和林离都指向 `controller-local`（7420），一键导入 Token（C-39 / D-33）也只认 `controller-local`。拆的时候：

- 汐保留 `controller-local`，7420，Token 文件 `<AgentRoom>\node\deepseek\agent-server.token`
- 林离用新节点 `controller-local-codex`，7421，Token 文件 `<AgentRoom>\node\codex\agent-server.token`
- **C-44（契约，C酱）**：`node.importLocalToken` 的 id 从一个固定值改成一个本机节点白名单（`controller-local`、`controller-local-codex`），每个 id 对应 main 设置里各自的 Token 文件路径；仍然只认回环地址，renderer 仍然不能传路径
- **D-40（汐）**：实现 C-44；推荐配置里林离改指 `controller-local-codex`；已有数据库里林离的参与者从 `controller-local` 迁到新节点（迁移脚本 + 真库副本验证），讨论和聊天都走新节点
- **切换顺序**（林离复审意见：过渡期不能让林离的命令行跑在汐的账号下）：
  1. 现状不动：7420 照旧是现在的节点（江浩的账号，带 `codex-*`），**汐的记忆文件夹先不建**，所以这段时间没有记忆可泄露
  2. S-20：以 `agentroom-codex` 起 7421（只有 `codex-*`），建林离的记忆文件夹
  3. D-40：林离的参与者迁到 7421，真库副本验证讨论和聊天都走 7421
  4. 之后才切汐：7420 删掉 `codex-*`，改为 `agentroom-deepseek` 运行（`agent: "deepseek"`，带别人的 profile 就拒绝启动），再建汐的记忆文件夹、打开她的记忆来源
  - 任何时候 `agentroom-deepseek` 账号下都不会跑 Codex；第 3 步之前林离走旧 7420，第 3 步之后走 7421

#### 留的位置（现在只占位，不实现）

**强记忆插件**：以后聊天里能插入复杂的记忆插件（按话题检索、自动整理、长期画像等）。接口位置定在**节点的「记忆读法」**上，主控端和数据流不变：

- 插件替换上面「哪些文件算候选 / 顺序 / 截断」里挑条目的部分；节点照旧负责包边界（core 的同一个包裹函数）、算 hash、回报清单。所以插件的输出照样在不可信边界里，主控端照样只存清单
- **每个插件一个单独的低权限账号**（例如 `agentroom-plg-<插件 id>`），和节点账号分开，也不和别的插件共用（汐、林离评审意见，和 ADR-004 §6 一致）。权限见上表：这位秘书的记忆正文只读，只有自己的 `ext\<插件 id>\` 能写；读不到节点配置、Token 和命令行登录信息；防火墙按账号默认禁止联网
- 节点**校验插件返回的条目 id 必须以 `ext/<这个插件的 id>/` 开头**，否则整次结果作废、按 `unavailable` 处理。插件不能冒充 core 或别的插件的条目
- 插件要拿到「这次在聊什么」才能检索，到时要在 `StartRun.chat` 上加一个字段：**只放当前这条用户消息的文字**，不放整份 Prompt、不放历史和别的秘书的发言；只给插件做检索用，不拼进 Prompt（所以不影响 Snapshot hash）。那是新的契约 PR，现在不加
- `ext\<插件 id>\` 不进聊天导出；卸载插件时经江浩确认后删除
- 加载插件那天的验收在 ADR-004 §6 的哨兵测试上加两条：插件读节点 Token 被拒、插件写别的插件的 `ext` 被拒
- 「秘书自己写记忆」也走插件或「一键记下」：只写 `inbox\`，江浩确认后才进正文。1B 仍然只读

**世界板块**（给秘书生活的虚拟空间 + 连接外部真实世界）：以后单独写 ADR。和记忆的关系现在先定三条：

- 世界里发生的事要变成记忆，只能写进这位秘书的 `inbox\`，和「一键记下」走同一个确认
- 世界读秘书的记忆，只能通过节点的记忆读法，不直接读文件夹
- 世界自己的数据放 `<AgentRoom>\world\`，不放进 `memory\`

- **一键转议题**：在聊天里选几条消息 → 「转成议题」→ 新建议题，选中的消息作为议题的初始材料（附件形式，标明来源会话），之后照讨论室流程盖章发送

### 3. 工作部分（简化版远程模式）

桌面先做，手机 1D 复用同一套控制 API：

- **一个列表**：进行中的议题和（1C 起）任务，每行一句状态（「第 2 轮 · 汐回答中」「等你盖章」「v2 已定稿」）
- **一个待办角标**：所有「等你盖章 / 等你确认」的事集中在这里，点进去就是原来的确认页
- **一个详情**：时间线只读 + 当前可做的动作按钮（发下一轮、汇总、定稿、暂停）。动作和讨论室完全是同一组命令，不另造一套
- 1C 以后加：任务进度、分支、PR 链接

### 4. 手机端

- 底部四个标签（2026-10-23 修订，参考微信）：**聊天 / 讨论室 / 秘书 / 我**。原来的「工作部分」并进「讨论室」标签：最上面是「等你处理」（盖章、确认，带红色角标），下面是进行中和已定稿的议题；「秘书」是三位的资料、人设、记忆、额度
- 聊天是手机端的**首页**
- 外观：苹果风格（玻璃质感的悬浮标签栏和菜单、带弹性的过渡动画，系统「减少动态效果」打开时只做淡入淡出）+ 微信的用法（长按菜单：复制 / 引用 / 多选 / 转发 / 转议题，置顶、免打扰、搜索、草稿、未读红点）。设计稿：画布《1B 外观草案》
- **讨论室按同一套风格重排**（2026-10-23 用户决定，只改界面，流程和状态机不变）：
  - 桌面三栏：左边议题按「等你处理 / 进行中 / 已定稿」分组；中间时间线；右边「方案与参与者」，**可以收起**
  - 每轮开头一个小胶囊（第 N 轮 · 盖章时间 · 用时），等盖章时变浅红；标题下一排进度药丸
  - 汇总卡用标签切换「要点 / 风险 / 遗漏 / 谁同意什么」
  - 底部输入卡：「发给」彩色小按钮 + 本轮任务 + 「去盖章」
  - **新建议题页**：名称、第一条发言、材料（可带聊天转来的消息和文件）、参与者、「先写一版方案」开关；创建不发给任何人
  - **按住盖章**：盖章按钮要按住一秒、进度走满才生效，中途松手不算（盖章发送和盖章定稿都一样）。按满只发**一次**命令；手指移出、失焦、页面隐藏、按钮变灰都会清掉计时；普通点击不能绕过。键盘：按住空格或回车一秒，规则相同。后端原有的指纹和状态校验照旧，动画本身不算批准
  - 草稿方案不显示「定稿」按钮，确认之后才出现（和方案状态机一致）
- 界面从一开始按手机宽度设计（桌面上是同样的布局放宽）
- **手机怎么连回主控机仍放在 1D**：要单独做安全设计（不把主控机直接暴露到公网，配对、Token、断线重连）。1B 只保证契约和界面能直接复用

### 5. 信息模型（新增，全部在 `packages/schemas` 定义）

```
聊天会话 Conversation（单聊/群聊、成员、标题、最近活跃时间）
 └─ 聊天消息 ChatMessage（发送者、内容、@ 了谁、引用的记忆来源、关联的 Run）
参与者 AgentProfile 新增：chatPersona（聊天人设）、memorySource（记忆来源配置）
议题 Topic 新增：fromConversation（从哪个会话转来，可为空）
```

每条 Agent 回答仍是一个 Run，**每个 Run 恰好一个终止事件**，和 Phase 0 / 1A 一样。

### 6. 节点侧

- 每个 Agent 多一个「聊天 profile」（如 `claude-chat`、`deepseek-chat`、`codex-chat`），和讨论 profile 分开：
  - 只读、无工具；Codex 的聊天 profile 用单独的 `CODEX_HOME`，只加载聊天人设，不加载工程规则
  - 读记忆文件夹的路径写在节点配置里，主控端只存「这个 Agent 有记忆来源 X」，不存路径和内容（数据流见 §2）
  - 「只能说话」是两条**分开验证**的保证（林离评审意见），只查配置字符串或问模型「你能不能写」都不算数：
    - **不能用工具**：检查真实启动参数里的工具 / 权限配置，并用真实的三个聊天 profile 实际尝试调用命令，核对被拒绝
    - **只能读记忆文件夹**：靠节点的低权限账号保证；用哨兵文件实测（见任务板 S-20）
- 1B 一起解决：Codex 讨论/聊天时能读整个硬盘的问题（节点用单独的低权限 Windows 账号运行，只能读自己的文件夹和记忆文件夹）

## 分阶段（替换 ADR-002 的 1B 一行）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **1B-1 外观** | 头像、聊天背景、配色、排版打磨 | 用户看过说「不粗糙了」 |
| **1B-2 聊天空间** | 单聊 / 群聊、聊天人设、记忆来源（节点文件夹 + 历史）、一键转议题；聊天 profile 只读 | 三位各单聊 10 条 + 群聊 1 次；转成议题后能正常跑一轮；聊天里无法触发任何文件改动 |
| **1B-3 参与者** | Agent 控制台、额度显示、替补 | 额度用尽时自动缺席并在汇总表里正确显示；替补走命令（不再写库模拟 0-B #10） |
| **1B-4 讨论室待办** | 讨论室标签里的「等你处理」+ 议题一句话状态（原「工作部分」） | 只用手机布局的讨论室标签完成一轮：发送 → 汇总 → 定稿 |

1C（执行）、1D（手机连接）不变。

## 不做 / 推迟

- Agent 之间自动接话、自动多轮
- Agent 自己写记忆（1B 只读）
- 读取云端应用的记忆、读取本机凭据
- 手机直连（1D）
- 聊天里直接触发执行

## 风险

1. **成本**：聊天不盖章，发得快、额度用得快。每条回答显示用量；群聊默认全员回答，人多时提醒
2. **人设和评审互相串味**：聊天用完整人设、讨论用三句，profile 和人设字段都分开
3. **记忆泄露**：记忆文件只在节点上读，进上下文时放在不可信边界里；聊天记录导出前要确认
4. **范围膨胀**：讨论室待办只做「看 + 原有命令」，不新增动作类型；聊天的新消息类型（语音、表情、文件）只在聊天里用
5. **语音转写**：本地转写的准确度和速度要实测；转写错了你可以在发送前改
