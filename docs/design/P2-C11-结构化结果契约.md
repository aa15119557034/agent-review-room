## 协商与旧协议

`NodeHealth.capabilities.structuredResults = {version: 1, profiles: [...]}` 只声明列出的普通文本 profile。`StartRunRequest.structuredResults = {version: 1}` 只开启本次 Run。缺能力、profile 不匹配或本次未开启均不能发送 `result_display`；旧节点的请求必须整个省略新字段，不能发 `false`、`null` 或空对象。首片不用于 image/world Run。

`canEmitStructuredResults` 是已 parse 对象的纯判定函数，供后续准入和发送边界共用；本 PR 不调用它启动功能。客户端派发前检查 capability，节点准入后记录本次开关；同 RunId 重发必须核对开关一致，不能在重试中改变事件格式。能力或版本不符时明确拒绝已要求新能力的请求，不能去掉开关偷偷重试。未开启的旧请求照常工作。

新事件是 `{type: "result_display", seq, ts, result: {version: 1, block}}`，映射到内部事件时加原有 `eventId/runId`。`RemoteEvent` / `AgentEvent` 保留旧联合类型；`StructuredRemoteEvent` / `StructuredAgentEvent` 复用旧成员并加展示事件，只有后续完成协商与存储接线的消费者才使用。沿用 Run 事件的排序、重放和去重规则；不能创建第二条事件通道。即使开启，`message_complete.text` 也必须包含完整权威正文，不能只剩引用占位符。展示事件不能代替终态、权限决定或独立验收证据。

`result_display` 只能出现在 `started` 之后、`terminal` 之前；`usage` 允许在 `message_complete` 之后（固定 fixture 即此顺序）。终态后到达的展示事件一律丢弃并记诊断，不能更新旧记录或复活 Run。D08/S07 消费端负责执行时序约束；单个事件 parse 成功不等于整条事件流合法。

冻结样本在 [structured-results fixtures](../../packages/schemas/test/fixtures/structured-results/README.md)。旧 health、StartRun、accepted 和 NDJSON 在修改 schemas 前由该基线解析并编码，保存文件 SHA-256。回归逐字节比较 UTF-8 JSON + LF，包括中文、多行和 emoji。它证明这些固定样本在**契约解析/编码**处不变；真实发送端双重协商、重连和旧客户端验收必须随 S07/D08 实现验证，不能用本测试宣称已经上线。

## 展示块

| kind | 内容 | 使用约束 |
|---|---|---|
| citation | citationId、SourceReference、可选标题 | 引用 ID 在同一 Run 内稳定；材料正文保存在已有 Message/ChatMessage，事件不复制一份正文 |
| tool_step | stepId、工具名、状态、简述 | 相同步骤 ID 更新进度；completed 仅为运行方报告，不证明文件落盘、进程停止或测试通过 |
| usage | scope=run、输入/输出 token、工具次数、费用 | 截至当前 seq 的累计快照，重放不能累加；分别记录 token 与工具次数 |
| unsupported | 原展示类型和原因 | 上游未知**展示**内容显式归一化，不保存原始 payload；已知块的坏结构不能用 unsupported 掩盖 |

计数/费用都强制区分 `{status:"unknown", reason}` 与 `{status:"measured", value:0}`（费用用 amount/currency）。不返回用量时必须保留 unknown；估算不冒充 measured。没有预算执行契约，`max_tokens` 不是整个任务的金额上限。

展示文字一律当不可信输入，包括 `citation.title`、`tool_step.summary`、`unsupported.originalKind` 和工具名。界面只按纯文本显示，不解析 Markdown/HTML、不自动变链接；进入其他秘书的 Prompt 时走 `wrapChatUntrusted`。来源 URL 只有用户显式打开时才交系统浏览器，并重新检查 HTTP(S)；应用不直接请求或自动预取该地址。URL 通过格式校验不表示通过节点的网络访问政策。

所有新对象 strict。未知 Room 事件、版本、块、执行或权限语义解析失败，不能默认当作成功或转为已完成工具步骤。上游块只有被适配层识别为纯展示数据后才可归一化为 unsupported；不明语义必须拒绝。坏流/截断在后续消费端记录诊断与真实失败原因，不能因为收到局部文字或展示块就完成 Run。

## 来源与既有实体

`SourceReference` 记录 source、version、contentHash、retrievedAt、status。source 使用现有 MessageId / ChatMessageId 或 HTTP(S) 网页定位，不是新资料库 ID。MessageId 移到 common 以避免循环依赖，entities 的原导出保持。首片不开放私人笔记或厂商文件句柄。

- 本地消息版本使用不可变记录 ID；网页有可信版本标识时记录该标识，没有则用已取回正文的 SHA-256。相同来源不同版本/hash 是不同内容，旧引用不能静默指向新版。
- contentHash 是可读正文原始 UTF-8 的 SHA-256；只有摘要不算取回正文。版本或正文未知显式为 null。readable 必须两者都有；missing/revoked 可以保留已知旧版本/hash，但不能由此重新授权读取。
- retrievedAt 是本次检索/取回记录时间，不等于发布日，也不保证正文成功取回。网页位置只用于定位；URL 合法不代表可访问或可分享，禁止内嵌用户名/密码。运行层仍须检查网络访问政策、项目归属和可见性。
- 可选 sourceRefs 附到既有 Message、ChatMessage、PromptSnapshot、ChatSnapshot；与所属记录在同一事务写入，写入后不可修改（包括版本、hash 和可读状态）。无引用时省略而不是写空数组。上限 100 是项目本次元数据限额，不声称是服务端限额。
- `Snapshot.sourceRefs` 位于 content 之外，**不受 Snapshot.contentHash 保护**。它仅用于展示和溯源，不能作为「模型确实读过这份资料」或「盖章绑定了这些来源」的证据。如果以后需要盖章绑定来源，须另开契约，参照附件将来源清单写入 content，让 contentHash 覆盖；本次不改变现有 hash 语义。
- 可读状态是当时记录；撤回、重新解析只影响后续使用，不回写旧消息或旧 Snapshot 的 sourceRefs。后续 Prompt/分享/搜索必须重查撤回和内容版本。D08 须沿用 X-35 stale 传播和 wrapChatUntrusted，不新建消息库或投影表。消息附属引用和事件必须与既有事务/备份一起保存，切库/取消后的旧回调不能写回。
- D08 解析 `source.kind="message"` 必须核对记录属于当前项目，不能仅凭 MessageId 查到就显示（F14）；ChatMessageId 同样核对当前会话/授权范围。来源记录本身不授予跨项目、跨会话读取权。

`chatMessageBase` 有意保留用户/秘书消息共用的引用挂载位；这不开放用户输入接口直接提交可信来源元数据。D08 首片在聊天消息中只由 main 为秘书回答写入 sourceRefs，用户粘贴 URL 仍是原始消息正文，不自动转成引用或触发取回。以后若启用用户消息的来源记录，仍需 main 核验来源、归属与可见性。

这份契约只校验边界形状；来源 hash 对应实际正文、跨项目权限、撤回传播、数据迁移和派生上下文仍由 D08/S07 验证。provider opaque、上传授权/接口、Goal、语音和调度均未加入。
