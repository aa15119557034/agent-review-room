# P2-C11b：项目检索批准、原件接收与来源查询契约

状态：**独立契约提案，待 C酱评审、江浩批准并合并；没有运行实现。**

依据：[P2-C11](P2-C11-结构化结果契约.md)、[P2-D08](P2-D08-资料引用存储.md)、[P2-S07](P2-S07-独立检索首片.md)，以及 [#261 的合并后交接](https://github.com/aa15119557034/agent-review-room/pull/261#issuecomment-6932840416)。#260 / #261 已合并，本提案从 main `994fe59` 起草。林离负责，C酱评审；此次 `packages/schemas/` 属交接明确允许的目录例外。

## 1. 范围与兼容

只接**项目/讨论中的一次查询 → 一次 Search → 至多一次 Fetch → 项目资料原件**。复用 PromptSnapshot、Approval、Run、messages.source_input 和 run_events；不新增调度器、消息库或展示投影表。不自动重试，不选替代 profile，不把资料自动发给秘书。后续在讨论中选用材料仍走现有快照和批准。

聊天网页引用、文档上传/云端数据发送授权、世界模型、Harness 写工具不在本片。检索批准只允许发送显示出来的查询；不隐式带聊天历史、项目笔记、片段、附件、工程 commit 或系统提示。

本 PR 只提供 schema、纯序列化/能力判断函数、测试和本说明。`PROJECT_RESEARCH_COMMANDS` / `PROJECT_RESEARCH_QUERIES` **尚未合入运行中的 COMMANDS / QUERIES**，现有 ControlCommand / ControlQuery 仍拒绝这些入口。新的远端可选字段不代表节点已经支持该能力；下一片完成实现及验收后才上报。

旧 RemoteEvent、StructuredRemoteEvent、AgentEvent 和已有事件查询不扩成隐式检索通道；旧节点、快照及 C11 fixture 序列化不变。两份 opt-in 均省略时保持旧行为；C11 structuredResults 不能代替新的检索能力。

## 2. 准备与批准

契约位置：`packages/schemas/src/control-api.ts`。

| 命令/查询 | 权限 | 输入 | 结果/规则 |
|---|---|---|---|
| `research.prepare` | author | projectId、已配置 nodeId/profileId、query | 同一事务创建不可变计划、PromptSnapshot、READY_FOR_REVIEW Approval；返回 ProjectResearchPreview；不调用付费 Search/Fetch |
| `research.preview` | read | projectId、snapshotId | 从当前库读取已存的计划、快照、批准；不能按现在的节点设置重建历史计划 |
| `research.approve` | approve | approvalId、expectedSnapshotHash、expectedResearchHash | 校验后以既有 CAS/唯一 Approval→Run 约束批准并创建一个 Run；返回对应 approval/run |
| `research.result` | read | projectId、runId | 返回 Run、已存计划、originalMessageId（未存原件为 null）、现有 run_events 的展示投影 |
| `approval.reject` / `run.cancel` | 现有权限 | 现有输入 | 复用既有状态机；取消仍不是云端未计费或远端进程树已停止的证明 |

首片目标选择复用已有设置中的节点及管理员 `nodes.list` / `node.test`，不新增公共网络发现服务。main 从已配置的 nodeId 获取 URL/凭据并核验 health，renderer 不能在 prepare 传地址或 Token。查询是 1–128 个 Unicode 码点，不允许孤立代理项或首尾空白；UI 可以在准备之前修整输入，准备后的查询不再 trim、拼装或改写。

`ProjectResearchPlan` 包含 version=1、projectId、snapshotId、query 和 target(nodeId、规范 baseUrl origin、profileId)。它是现有快照的不可变附属元数据，不是第二种快照实体。实现时与快照、批准同事务持久化（现有 prompt_snapshots 的可空附属列；旧记录为空），不得只留在内存或从可变节点设置推断用途。

快照 `content = query`，`reviewerAgent = profileId`，`adapterVersion = "project-research-v1"`，contributionIds 为空，不带 sourceRefs、项目笔记和附件，工程字段为 null。原有 `contentHash = sha256(UTF-8(content))` 保持不变。另存 `researchHash = sha256(UTF-8(projectResearchApprovalContent(plan)))`，规范内容是按以下固定顺序排列的 JSON 数组，无额外空白或换行：

```text
["room.project-research",1,projectId,snapshotId,query,nodeId,baseUrl,profileId]
```

main 创建、读取、批准时均重算两份 hash；schema 只校验格式，不能代替实际 SHA-256 核验。批准页显示查询、节点地址、profile、最多 1 Search + 1 Fetch、费用未知/按公开价格的估算说明，不能把估算填进 measured cost。

批准及真正派发前重读当前配置、项目归属和两项节点能力；地址/profile/查询/hash 不一致返回 `stale_snapshot`，能力不支持或不可达返回 `agent_unavailable`，不清除 opt-in 降级重发。匹配到已决定的批准走既有 `already_decided`，不能重复生成 Run。跨项目/非检索 ID 返回现有 `not_found` / `invalid_state`，错误不附带其他项目正文。

**所有普通批准/批量派发路径必须识别存储中的 research 元数据并拒绝走普通 Reviewer。** 检索计划只能由 `research.approve` 批准；缺元数据不能仅凭 adapterVersion/profile 名猜成检索；带研究拼装版本但缺元数据/元数据损坏时返回 invalid_state，也不能退成普通 Run。同一研究快照也不能插入讨论批次绕过第二份 hash。批准后节点地址变化不能用新地址续派或重连；未派发先失败，已启动只用批准时捕获的目标做取消/收尾。

首片没有自动恢复/重跑：启动修复复用已有中断 Run 处理，用户重新准备、批准才产生新的付费调用。重发同 RunId 须比较所有既有身份字段以及 projectResearch / structuredResults；同 RunId 换开关、查询或 profile 必须冲突，不能再次请求厂商。

## 3. 远端能力和原文顺序

契约位置：`packages/schemas/src/remote-protocol.ts`。

health 增加可选 `capabilities.projectResearch = {version:1, profiles:[...]}`。列出的每个 profile 必须同时存在于 health.profiles 和 capabilities.structuredResults.profiles。请求同时带 `projectResearch:{version:1}` 与 `structuredResults:{version:1}`；`canRunProjectResearch` 仅接受已解析对象，按实际所选 profile 核对。缺任一项即不支持。

检索请求只接受纯文本、固定模型的专用 profile；拒绝 chat（包括 memory=null）、model、附件、图片槽、kind=image、工程 commit 和世界绑定。StartRun.snapshot.content 是已批准查询原文，节点照常先验证 contentHash。节点只能在真正实现下述协议后声明能力，不能只因使用 room-jsonl 或支持 result_display 就上报。

协商后的客户端使用 `ProjectResearchRemoteEvent`，允许 started、output（仅诊断）、result_display、heartbeat、message_complete 和 terminal。不允许 text_delta、prompt_final 或 permission_request，避免把未完整的网页先作为资料显示。

`message_complete` 在此协商模式下增加**必填** `source`：

- 成功 Fetch：text 是完整的可读正文；source 是 status=readable 的网页 SourceReference，contentHash 与 version 都是该 text 的 UTF-8 SHA-256。正文最多 512 KiB UTF-8，非空、不截断、不 trim、不换行归一化；孤立代理项拒绝。节点和 main 各自重算，不信任事件中的 hash。
- Search 无结果/没有取回原件：source=null，text 是明确的无结果说明；不生成 source_input，不伪造可读引用。失败继续走失败终态；缺失引用的 version/hash 可以为 null，不能把 snippet 当正文。
- 每个 Run 最多一个 message_complete。元数据与原文在同一事件中到达，正文只传一份；不另开原件下载端点，不把完整 HTTP 响应、厂商状态或密钥塞入事件。

成功顺序：

```text
started → search/fetch 步骤 → message_complete(text + source)
        → main 校验并提交 source_input + Run 原件关联
        → result_display(citation) → result_display(usage，可选) → terminal(completed)
```

客户端必须按 seq 串行等待写队列；后续事件到达不代表先前提交已完成。完整原文通过核验后，在一个事务内写 `source_input`（带相同网页自引用）及现有 runs 上的可空原件关联；只在提交成功后接受对应可读 citation。原件关联用于 `research.result.originalMessageId`，不增加原件表。归属固定为启动时的项目、快照和库实例，不能由事件提供或覆盖。

引用的 URL/version/hash 必须与本 Run 已提交原件一致，既有同项目其他原件不能充当本次 Fetch 成功。引用先到时立即拒收并记诊断，不缓存等待原件，不在原件到达后回放补收；同 seq 的已拒绝事件仍拒绝。重连重复原件/引用须幂等核对持久的 Run 关联、seq 和内容，不能重复插入；同 seq 或同 Run 原件被改写属于协议错误。普通诊断只记录原因/Run/seq，不记录正文、凭据。

不修改已合并 D08“引用不可先于原件”的边界来迁就旧 producer。下一片调整节点的缓冲/flush 顺序：当前 room-jsonl 的 done 只设置 verdict，message_complete 在进程关闭时生成，所以**只把 CLI 的 done 行移到 citation 前不够**。要在成功关闭、完整原文已确定后先发 message_complete 再发引用；执行失败/缺 done 时不能发成功原文。原文入库失败也不能最终发布成功资料回复，走既有 postprocess/error。

原件在后来取消/失败之前已成功提交的，保留它作为确实取回的历史资料；不把 Run 标成功、不生成普通 reviewer_output、不自动加入讨论。取消后的旧回包不能再新建原件/引用。UI 同时显示真实 Run 状态，不能用有资料/工具步骤 completed 推断整个 Run 成功。

## 4. 取消、切库与迟到回包

这些是下一片运行实现的强制条件，**单个事件 schema 通过不证明满足这些条件**：

1. 请求开始时捕获 db 实例、工作区代次、projectId、snapshotId、两份 hash、RunId、批准的 target；不要在异步回调中读取全局“当前库”写结果。
2. 接收时、进入写队列后、事务实际提交前核对取消信号、代次、db.open、Run 生命周期/所有权和原快照绑定；任一失效即拒绝，旧回包不能转投新库。取消/切库要先失效化上下文，再等待在途操作收尾。恢复同路径或相同 ID 的另一份库仍是新代次。
3. started 前或首次 terminal 后新到的原文/展示事件拒绝；已在正常终态之前入队的事件可以按 FIFO 完成，再提交终态。取消、切库不适用这个继续写入的例外，已排队但尚未提交的写入也拒绝。
4. prepare/approve 的 health await、来源查询/预览及 renderer 的异步返回也受工作区代次约束；旧工作区的预览、批准或成功提示不能进入新工作区。检查必须在 await 之后重复，不能只在入口检查。
5. 新控制查询仍使用现有 ControlError；数据库/IO/损坏/网络错误作为错误上抛，不吞成 missing、空数组或 measured 0。D08 的撤回传播、批准/派发/最终发布前来源复查继续保留。

## 5. 来源当前状态与原文预览

| 查询 | 输入 | 响应 |
|---|---|---|
| `sources.current` | projectId + owner(message/snapshot 的已有 ID) | projectId、owner、checkedAt、全部已存引用；每项 index、**原样的历史 reference**、单独的 currentStatus |
| `sources.preview` | 同一 owner + 引用 index(0–99) | 再次检查后的 reference、checkedAt、status；readable 时 content 是匹配的原文，missing/revoked 时 content 必须 null |

main 先验证 owner 属于请求项目，再读它不可变的 sourceRefs；返回顺序不变、index 从 0 连续。没有引用返回空列表，owner 不存在/越界返回 not_found，跨项目不泄露内容。renderer 不能传 URL、SourceReference、文件路径或任意 chat_message ID 请求取回。即使项目 owner 内部引用聊天消息，也必须经过 D08 的显式分享/撤回校验，不能绕过项目共享读取私人聊天。

这是**当前库中的可读性检查**，不探测网页在线状态，不重新 Fetch，不打开远程正文或替换旧版本。missing 表示指定原件/版本/hash 不可用；revoked 表示当前授权/依赖已撤回；未知错误走 ControlError。历史 reference.status/version/hash/retrievedAt 不改写，未取回的历史记录不能因同 URL 后来有了正文就升级为 readable。

批准页用 currentStatus 区别于“记录时可读”；发现失效时沿用 C12 的 stale_snapshot 重建入口。checkedAt 只是检查时间，不是批准令牌；批准、派发和最终发布仍再次复查。预览缓存至少按工作区代次、projectId、owner 与 index 隔离，切项目/切库/撤回时清空正文并递增本地查询代次；晚到结果不能重新显示已撤回原文。

`research.result` 只读取 run_events 投影，保留累计 usage 覆盖规则，未知费用/用量仍 unknown。首片最多 200 个投影块，超过属于协议/数据错误，不静默截断；可读 citation 必须已有原件关联。预览该原件用它的 MessageId 作为 owner，不增加任意 Run/URL 原文读取接口。

## 6. 验收与下一片

本 PR 的确定性 schema 测试覆盖：两项能力/两份 opt-in、错误版本、请求范围、绑定序列化、项目/快照关联、Unicode/UTF-8 上限、原件元数据、历史/当前状态分离、不可读原文不得返回、控制入口尚未启用、旧 fixture 兼容。hash 格式通过不代表正文正确，运行时权限/IO/生命周期仍需下面的集成测试。

| 下一片必测场景 | 必须观察到的结果 |
|---|---|
| 准备、拒绝、重复批准、普通/批量入口绕过 | 准备/拒绝 0 次厂商调用；同批准至多 1 Run；绕过拒绝 |
| 地址/查询/profile/hash 改变，health await 中切库 | 不派发，不自动换目标/降级；旧库和新库无迟到新增 |
| 成功、空结果、Fetch 失败、正文/hash 不匹配 | 成功原件先落库；无结果不造原件；hash 错误无成功发布 |
| 引用先于原件、重复 seq、同 seq 改写、重连 | 先到引用不补收；合法重放不重复写；冲突明确拒绝 |
| 原文入队期间取消/切库/关闭，再恢复相同 ID 库 | 不写新库、不写尚未提交的旧回包；无迟到成功提示 |
| 原件已提交后取消/失败 | 保留已提交事实，Run 仍取消/失败，无自动讨论/Reviewer 回复 |
| 当前来源撤回、跨项目 ID、预览期间撤回/切库 | stale_snapshot/拒绝/正文隐藏；不能读私人聊天或返回旧正文 |
| 备份、恢复、重启 | 同一原件版本/hash 可定位；中断 Run 不自动付费重跑 |
| 不协商能力的旧节点/旧请求 | 行为和序列化保持兼容，不擅自添加新字段 |

契约评审合并后再开接线 PR：桌面入口 → 专用节点 profile → D08 原件/引用 → C12 当前状态与预览。并补 #260 两条建议：标题按完整 Unicode 字符截断且仍满足 C11 的 500 UTF-16 单元上限（不拆代理对）；URL 策略拒绝也有 fetch failed 步骤。真实 API 验收另列调用次数、日期和费用信息；本契约 PR 不调用 DeepSeek，不产生 API 费用。
