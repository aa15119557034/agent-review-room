# ADR-002：讨论室模式（多 Agent 群聊 → 方案 → 分工执行）

- 状态：**提议中**（等用户批准）
- 日期：2026-10-21
- 提出：Claude ｜ 评审：DeepSeek ｜ 批准：用户
- 界面依据：Design 画布《讨论室界面草案》v3（11 张画面，含「0-A 页面结构」「0-B 一轮的状态与记录」），用户已确认

## 背景

Phase 0 已验收（`docs/Phase0-验收记录.md`）：一段原文 → 选片段 → 生成 Prompt → 人盖章 → 远端 Reviewer 回答 → 结果入库，整条链在两台 Windows 真机上跑通。

用户要的不止"一次评审"，而是一个**群聊式讨论室**：

- 用户发议题（文字 / 文件），勾选这一轮让哪些 Agent 发言
- 多个 Agent（Claude、DeepSeek、Codex）同时回答，**每一次发出去都要用户盖章**
- C酱（Claude）汇总分歧、补充遗漏，形成**方案的新版本**，用户确认后推回下一轮
- 反复迭代到用户**盖章定稿**，再由 C酱 拆任务，各 Agent 在自己的电脑上开分支执行，经 GitHub 整合
- 中途可以暂停、打断、补充、改方向；Agent 可以单独停用（比如额度用尽），任务临时交给替补，之后交还

这超出了 V0.4 冻结设计的范围，按规则先写 ADR。

## 决定

### 1. 不推翻 Phase 0，在它上面加一层

Phase 0 的四条底线全部保留，并扩展到群聊：

| Phase 0 的底线 | 在讨论室里 |
|---|---|
| Prompt Snapshot 不可变 + SHA-256 | 每个收件人一份 Snapshot，确认页并列显示指纹 |
| 人批准后才发送，批准时校验 hash | 一次盖章覆盖这一轮的所有收件人，逐个校验 hash |
| 每个 Run 恰好一个终止事件 | 一个 Agent 的一次回答 = 一个 Run，不变 |
| 其他 Agent 的输出一律当作不可信数据 | 讨论记录、附件、其他 Agent 的发言都放进带 nonce 的边界 |

### 2. 信息模型（新增实体，全部在 `packages/schemas` 定义）

```
议题 Topic（复用 Project）
 ├─ 消息 Message（复用：source_input / reviewer_output，新增 human_note、summary）
 ├─ 轮 Round ─┬─ 轮批准 RoundApproval（一次盖章，列出 N 个 {agent, snapshotId, contentHash}）
 │            └─ Run × N（每个收件人一个，引用 RoundApproval 中属于自己的那一项）
 ├─ 方案版本 PlanVersion（v1 → v2 → …，记录「基于第几轮、谁起草、谁确认、是否定稿」）
 └─ 任务 Task（定稿后才有；记录负责人、替补、交接说明、分支、PR）
参与者 AgentProfile（头像、角色、参与讨论/执行/汇总、计费方式、替补、权限、所在节点）
会话 Session（执行阶段一个 Agent 的一个上下文窗口；Handoff 交接说明把新旧会话连起来）
```

- 「一个 Approval 最多一个 Run」改成「**RoundApproval 里每一项最多一个 Run**」，数据库用唯一约束 `(round_approval_id, agent)` 保证
- 每轮任务带来源：`你写的 / C酱 提议 / 上轮遗留`；汇总要点带来源：`你写的 / C酱 抽取 / 某 Agent 提出`

### 3. 一轮的状态（照画布 0-B 实现）

```
草稿 →(盖章)→ 进行中 ⇄ 暂停中
进行中 →(全员有结局 / 你点「结束本轮」)→ 待汇总 →(C酱 汇总)→ 已汇总（方案 vN）
已汇总 →(推回)→ 下一轮草稿 ｜ →(盖章定稿)→ 定稿
任意 →(回到某阶段改方向)→ 作废（记录保留，方案版本记回退原因）
```

几个语义定死（DeepSeek 评审提出，已采纳）：

- **打断** = 旧 Run 以 `cancelled(interrupted_by_user)` 结束，已写部分保留；补充后的内容**新盖章、新 Run**。两段都计额度
- **全部暂停** = 正在答的都按"打断"处理，计时停止；**恢复** = 同一内容一键重新盖章发起。生成中的回答不能冻结再续写
- **结束本轮** = 没答完的标「被中断」，直接进入待汇总
- **额度用尽** = 该 Run 的结局记为「缺席（额度）」，其他人继续；不是错误，也不是"没表态"
- **只发给一个人的补充** = 时间线标「他收到了额外信息」，汇总里注明
- **替补代答**：替补不能是汇总者；代答标「代 X」，**不用原角色设定**，在汇总表里单独一栏，不算同意或反对
- **讨论不会自己停**：没有自动多轮，什么时候定稿由用户决定

Run 的失败原因（`FailureReason`）需要新增：`interrupted_by_user`、`quota_exhausted`、`superseded`（被新版本取代）。这是契约变更，单独的契约 PR。

### 4. 盖章点（朱红色只用在这里）

发起一轮、发送补充、暂停后恢复、**定稿**、派发任务、合并非低风险 PR。

### 5. Agent 怎么接入：全部走 AgentServer

主控机上**也跑一个 AgentServer**（只监听 127.0.0.1），和用户电脑上的那个用同一套协议。好处是主控端只有一种 Adapter，以后加 Agent 只需加 profile。

| Agent | 位置 | 怎么调用 | 计费 |
|---|---|---|---|
| C酱 | 用户的电脑 | `claude -p`（已跑通） | Claude 订阅 |
| Codex | 主控机 | `codex exec`（Codex 命令行，用 ChatGPT 账号登录） | ChatGPT 订阅 |
| DeepSeek | 主控机 | 节点上调 DeepSeek API（Key 留在节点，不进主控端） | 按量付费 |

桌面版 GPT 应用和 DeepSeek Harness 的网页界面都不能被程序调用，所以用上面这几个可编程的入口。Codex 需要在主控机上装 Codex 命令行，并用 ChatGPT 账号登录一次。

### 6. 额度和上下文状态

节点的 health 接口扩展为按 profile 报告。**读不到就显示「未知」，不猜**。

| 数据 | 来源 | 可靠性 |
|---|---|---|
| Claude 5 小时 / 每周额度、重置时间 | Claude Code 官方状态栏数据里的 `rate_limits.five_hour`、`rate_limits.seven_day`（只有订阅用户有） | 字段是官方文档写明的；`-p` 模式下能不能拿到要在节点上实测（S-10） |
| Claude 上下文用量 | 同上，`context_window.used_percentage` | 同上 |
| Codex 5 小时 / 每周额度 | `codex app-server` 的 `account/rateLimits/read` | 来自第三方资料，未见官方文档，需实测（S-10），读不到就显示「未知」 |
| DeepSeek 余额 | DeepSeek API 的余额查询接口 | 有公开文档 |
| 本议题累计 / 本轮预计 | 主控端自己算（预计按字数估，界面上注明误差） | — |

**不使用**：读取本机登录凭据去调未公开的用量接口。

### 7. 讨论记录怎么发给 Agent

- 最近 2 轮发全文，更早的轮次用 C酱 的汇总代替；确认页显示「压缩了哪几轮、摘要是谁在哪一轮生成的」，可以改成发全文
- 每个 Agent 的角色设定加在指令最前面；其他人的发言、附件都在不可信边界里
- 同一轮发给不同人的内容如果不一样（例如只给一个人的补充），确认页标出来

### 8. 存储

- **SQLite 是唯一的权威数据**，在主控机上
- 每个议题可以导出为一个文件夹（`议题.md`、`第N轮/`、`方案-vN.md`、`附件/`），在用户选的时机（默认：定稿时）推到 GitHub
- **每个 Agent 的工作目录按所在电脑分别设置**，记录里只存相对路径，换电脑也对得上；同一台电脑上的两个 Agent 各用一个文件夹

### 9. 执行阶段（最后做）

- 每个任务一个分支；Agent 只能读写自己的项目文件夹，运行命令每次问用户，默认不联网，只能推送自己的分支
- **会话交接**：上下文超过 85% 或压缩满 3 次时提示；旧会话写交接说明（做到哪、改了哪些文件、下一步），用户确认后新会话在**同一文件夹、同一分支**接着做
- **替补执行**：交接说明 → 替补接手 → 原 Agent 恢复后，替补再写交接说明交还
- **合并规则**（三档）：只改文档或测试、审核通过、测试全绿 → C酱 自动合并，事后通知；其他 → 用户点一次「盖章合并」；改契约或设计 → 永远要用户亲自批准，这一档不能关

### 10. 手机端（以后）

只连主控端的控制 API（`control-api.ts` 已预留 scope），不直接连任何 Agent。第一版只做：逐字查看并盖章、通知、议题只读。

## 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **1A 讨论** | 主页、发送确认、进行中、汇总与方案版本；Claude + DeepSeek 两个 Agent | 一个议题跑 3 轮并盖章定稿；画布 0-B 的 13 种情况各有一条测试 |
| **1B 参与者** | Agent 控制台、额度状态、替补、设置页（外观、存储、每个 Agent 的路径）；接入 Codex | 额度用尽时自动缺席并在汇总表里正确显示 |
| **1C 执行** | 分工、执行中、会话交接、GitHub 侧栏、合并规则 | 一个定稿方案拆成 3 个任务，各自开 PR 并按规则合并 |
| **1D 手机** | 手机端 | 在手机上盖章发起一轮 |

每个阶段都要用户验收后才进入下一个。

## 1A 的任务草案（批准本 ADR 后细化到 `docs/phase1-任务.md`）

- **C-20 契约**（Claude）：Topic/Round/RoundApproval/PlanVersion/AgentProfile、新的失败原因、讨论室的 commands/queries/events。单独 PR，用户批准
- **D-20 迁移 v3**（DeepSeek）：新表 + 唯一约束；从 v3 起 CHECK 写成字面量，不再随契约漂移
- **D-21 轮次编排**（DeepSeek）：一轮并行 N 个 Run；暂停 / 打断 / 结束本轮 / 缺席的语义；每个 Run 恰好一个终止事件
- **D-22 讨论 Prompt 拼装**（DeepSeek，core）：讨论记录压缩、角色设定、不可信边界、逐个收件人的指纹
- **C-21～C-24 界面**（Claude）：主页、发送确认、进行中、汇总与方案版本，先对着 mock 开发
- **S-10 节点**（Claude）：DeepSeek 和 Codex 的 profile；实测额度读取（第 6 节两个"需实测"）

## 不做 / 推迟

- 自动多轮（讨论不会自己停）
- 删除议题（沿用 Phase 0 的不可变决定）
- 替补带原 Agent 的角色设定
- 读取本机凭据调用未公开的用量接口

## 风险

1. **额度读不到**：Claude 的 `-p` 模式和 Codex 的读取方式都要实测，最坏情况是只显示「未知」，再加上我们自己统计的用量
2. **成本**：每轮 N 个 Agent 同时回答，讨论记录越长越贵。靠压缩、发送前预计用量和提醒线控制
3. **自动合并**：只对低风险改动开放，而且第一次启用前要单独确认一次
4. **复杂度**：先做 1A，确认讨论这一层真的好用，再往下做
