## 背景

用户 2026-11-02 在秘书页截图上标了：

- 「3 大项目 → 子项目 → 项目主体 + 各 agent 子文件」
- 「替补是默认设置，聊天单独一份调整」
- 「上下文 % 会话单独」「历史按项目」

外观部分（历史按议题 / 会话分组、上下文放进会话顶上）已经在 C-33b 第 3 次（#175）做了。剩下的要改数据结构，就是这份。

同一天用户又加了一件：**聊天设置里要能「换窗口」**。他的原话是：上下文压缩几次以后注意力下降得厉害，所以要能换窗口。这里换的是秘书这边的对话窗口，不是界面上的窗口。

## 决定

### 1. 分层：不加新的一层

| 截图上的层 | 对应什么 |
|---|---|
| 3 大项目 | 左边导航：聊天、讨论室、世界。不进数据库；世界以后单独写 ADR |
| 子项目 | 讨论室里一个议题（`Project`），聊天里一个会话（`Conversation`）。不加「项目包议题」的父一层 |
| 项目主体 | 子项目里现有的全部内容（时间线、方案版本、消息），不动 |
| 各 agent 子文件 | **新加：项目笔记**。每位秘书在每个子项目里有一份 |

项目笔记和长期记忆是两样东西：

- **长期记忆**（ADR-003 §2a）记的是「这个人是谁、和用户什么关系」。哪里都带上，只读，放在秘书自己的电脑上。
- **项目笔记**是工作本，记的是「这里我负责什么、做到哪了、记住了什么约定」。只在这个子项目里带上，秘书能写，用户能看、能改。

### 2. 用户选的四项

| 问题 | 选了 | 意思 |
|---|---|---|
| 1. 笔记放在哪 | **A** | 存在主控机的数据库里，和议题、会话放在一起。秘书电脑关机也能看，导出议题时一起带走 |
| 2. 谁能写 | **A** | 秘书自己直接写自己那份。每次写都存新版，旧版保留，能回退。长期记忆照旧只读 |
| 3. 能不能看别人的 | **A** | 发给秘书时只带他自己那份。用户在界面上能看所有人的 |
| 4. 替补按聊天单独调 | **B** | 聊天照旧不找替补（ADR-003 不变）。秘书页的替补只管讨论室；聊天里只能设「这个会话里他缺席时不发给他」 |

第 4 项选 B，截图上「聊天单独一份调整」这句就落成每个会话一个「缺席时跳过」开关，不是换人来答。

### 3. 项目笔记的数据

| 字段 | 含义 |
|---|---|
| `scope` | 属于哪个子项目：`{ kind: "topic", projectId }` 或 `{ kind: "conversation", conversationId }`。以后世界再加一种 |
| `agent` | 哪位秘书的 |
| `content` | 正文，Markdown，上限 20,000 字 |
| `version` / `parentId` | 每次改都存一个新版本（不可变），`parentId` 指向上一版；回退 = 拿旧版内容存一个新版 |
| `updatedBy` | `agent`（秘书自己写的）或 `human`（用户改的） |
| `reason` | `reply`（回答里顺手更新）、`window_handoff`（换窗口时写的交接）、`human_edit`、`revert` |
| `source` | 秘书写的时候，是哪一次回答：讨论室记 `turnId`，聊天记 `runId` |

秘书怎么写：

- 在回答里带一段 ` ```room-note ` 代码块，写法和 `room-chart` 一样（ADR-004 §5）。块里是**整份**新笔记，不是增量。
- 主控端把这段从回答里切出来，校验长度后存成新版。回答正文里不显示这段，时间线上显示一行「C酱 更新了笔记 · 看改了什么」。
- 一次回答里有多段 `room-note`，或者超过上限：这段笔记不存，回答照常，时间线提示「笔记没存上」。

发给秘书时：

- 把他在这个子项目的最新笔记放进带 nonce 的资料边界（和附件清单一样按不可信内容处理）。
- 笔记的版本 id 算进快照指纹，确认页上能看到这次带的是第几版。

### 4. 聊天里的「换窗口」

**为什么要换。** 聊天每次回答都是重新拼一份发出去：最近的消息带全文，更早的用历史摘要代替（X-35）。聊得越久，摘要叠得越多，秘书看到的就越是二手内容。换窗口就是让某位秘书**从一份交接笔记重新开始**，以前的消息不再发给他。

**在哪里。** 聊天设置（会话设置）里，每位成员一行，显示「当前第 N 个窗口 · 窗口里压缩了 M 次」，后面有一个「换窗口」按钮。

- 单聊只有一行。
- 群聊里每位秘书分开换；换了一位，不影响其他人。

**换的时候发生什么：**

1. 主控端起一个 `purpose = "window_handoff"` 的 Run。秘书照他现在的窗口内容，写一份新版项目笔记作为交接说明：做到哪了、要记住的约定、还没回答的事。
2. 用户在弹出单里看这份笔记，可以改。点「换」才生效，点「取消」就什么都不变（Run 的结果丢掉，不存成笔记）。
3. 生效时，在同一个事务里做三件事：
   - 存笔记新版（`reason = window_handoff`）
   - 记一条窗口记录
   - 在时间线插一行「C酱 换了新窗口 · 看交接笔记」

窗口记录（`ChatWindow`）：

| 字段 | 含义 |
|---|---|
| `conversationId` | 哪个会话 |
| `agent` | 哪位秘书 |
| `index` | 第几个窗口，从 1 开始（没换过的就是第 1 个，不写记录） |
| `startsAfterMessageId` | 窗口从哪条消息之后开始 |
| `handoffNoteVersionId` | 交接笔记的版本 |

**换了之后发给这位秘书的内容：**

- 长期记忆，照旧
- 他在这个会话的最新项目笔记（第一次就是交接笔记）
- 窗口开始以后的消息，照 X-35 的规则：最近的带全文、更早的用摘要

窗口开始前的消息和摘要都不发。被引用的旧消息也不展开，只写「引用了换窗口前的一条消息」。

**什么时候提醒换。** 某位秘书的「窗口里压缩次数」到 3 次，聊天顶上的记忆条显示「建议换窗口」（参照 ADR-002 §9 的「压缩满 3 次」）。只提醒，不自动换。

- 窗口里压缩次数 = 覆盖范围完全在这个窗口里的历史摘要有几份。主控端自己数，不用节点上报。
- 聊天顶上的「压缩 N 次」也改成显示这个数，就是用户标的「会话单独」。
- 「上下文 %」还是节点按秘书报的那个数，旁边标「节点报的」。按会话算要改远端协议，等需要了再说。

**讨论室不做换窗口。** 讨论室每轮都按轮重新拼，本来就没有越拼越长的问题。执行阶段（1C）照 ADR-002 §9 做会话交接。

### 5. 同步到 GitHub

用户 2026-11-02 原话：「同时按我们现在这样在 GitHub 同步，交流不好就上 GitHub」。

- 主控机数据库是准的，GitHub 是副本，也是备用的交流渠道，和现在三位秘书的做法一样。
- 1B 先做**单向导出**：设置里填一个用户自己的仓库后，项目笔记和换窗口时的交接笔记按 `notes/<子项目>/<秘书>.md` 提交过去。提交说明写清是谁、第几版、为什么改。
- 不从 GitHub 往回读。GitHub Token 只在 main 进程读（同 `AGENTS.md` 的密钥规则），不进 renderer。
- 不填仓库就不同步，其他功能照常。
- 执行阶段（1C）的 GitHub 侧栏照 ADR-002，到时再把「聊不通就去 PR / issue 上说」接进去。

## 不做

- 不加「项目包议题」的父一层
- 不让秘书写长期记忆（照旧只读、要用户确认）
- 聊天不找替补
- 不自动换窗口
- 不从 GitHub 往回同步
- 世界板块另写 ADR
