# ADR-001：控制面与执行面分离（Remote Proxy Mode）

- 状态：**提议中**（等用户批准；V0.4 已冻结，这条作为冻结后的第一份正式变更）
- 日期：2026-10-19
- 提出：DeepSeek ｜ 评审：Claude

## 决定

Orchestrator（控制面）不再只能通过本地 `child_process` 拉起 CLI。新增：

- `RemoteAgentAdapter`（`packages/core/src/adapter/remote-agent-adapter.ts`）：通过网络调用远端节点
- `AgentServer`（`apps/agent-server/`）：运行在隔离节点上，按本地配置拉起 CLI，把输出流式回传
- 协议：`packages/schemas/src/remote-protocol.ts`（HTTP + NDJSON 事件流，v1）
- 预留给手机 App 的控制面 API：`packages/schemas/src/control-api.ts`

## 放在哪个 Phase

Phase 0 的 Reviewer 是**直接调 API**（V0.4 §35），没有 CLI 可以代理，所以远端节点**不在 Phase 0 的关键路径上**。

- Phase 0：只把契约定下来（已完成草案），AgentServer 骨架作为 spike 存在，不接入主流程
- Phase 1：和 CLI Adapter 一起实现 `RemoteAgentAdapter`

## 状态机评估：有没有死锁

**结论：没有真正的死锁。** Approval 和 Run 的转换表都是单向的、最终落到终态，两者之间也不存在互相等待。真正的风险是两类：**无限挂起**（某个等待没有超时）和**裂脑**（两边对"这个 run 结束了没有"的判断不一致）。下面逐条说明，以及骨架里怎么处理的。

### 1. 等待人工审批时断线 → 无限挂起（最严重）

V0.4 §20 规定等待人工期间暂停 idle timeout。如果这时网络也断了，就没有任何计时器在走，run 会永远卡在 RUNNING。

**处理：把"连接是否活着"和"Agent 是否有进展"分开。**
- 心跳（heartbeat）只检测连接，**永不暂停**。节点每 `heartbeatMs` 发一次，Adapter 超过 `heartbeatTimeoutMs` 收不到任何字节就判定断线
- idle timeout 只衡量 Agent 进展，等人时可以暂停

### 2. 断线后两边判断不一致 → 裂脑

本地把 run 标成 FAILED，远端进程却还在跑，甚至还在写文件。之后用户重试，就有两个进程在改同一份代码。

**处理：事件流本身就是租约。**
- 节点上某个 run 没有任何订阅者超过 `leaseMs`，节点自己终止整个进程树
- Orchestrator 断线后在 `reconnectGraceMs` 内反复重连，超时才判 FAILED(connection_lost)
- **必须满足 `leaseMs < reconnectGraceMs`**（默认 20s < 30s）。这样远端一定先停，本地后判失败，不会出现"本地说失败、远端还在跑"的窗口
- Orchestrator 自己崩溃时同样成立：没人订阅 → 租约到期 → 远端自动停

已测试：租约到期后子进程和孙进程都被终止。

### 3. 不要把 RECOVERY_REQUIRED 加进 Run 状态机

DeepSeek 的提案里，断线后 Run 可以进入 RECOVERY_REQUIRED。这会破坏"终态不可再变"和"每个 run 恰好一个终止事件"这两条不变量：一个 run 如果之后还能"恢复"，它就不算真正结束。

**处理：**
- 短暂断线用 RUNNING 的内部子状态 `disconnected` 表示（和 `waiting_for_human` 同级），不改主状态
- 重连成功 → 回到 `active`，节点补发断线期间的事件，一条不丢
- 宽限期用完 → FAILED(connection_lost)，这是终态
- "恢复" = 新 runId 重试（V0.4 §22 原有规则）
- RECOVERY_REQUIRED 继续只用于 worktree（V0.4 §27）

### 4. 启动请求超时重试 → 重复执行

POST 发出去了，响应在路上丢了，Adapter 重试，远端就跑了两次。

**处理：** 节点按 runId 幂等。同一个 runId、同样内容 → 返回 `already_exists`；同一个 runId、不同内容 → 409。

### 5. 节点繁忙时 Approval 过期

节点满载（429）时，Approval 已经是 APPROVED，但 run 起不来。如果这期间代码变了，Approval 按 V0.4 §18 应该 EXPIRED。

**处理：**
- "消费 Approval + 创建 Run(QUEUED)" 在同一个事务里完成，用 `runs.approval_id` 唯一约束保证一个 Approval 最多一个 Run
- 节点繁忙时 Run 保持 QUEUED，**不要判 FAILED**，由 Orchestrator 的队列稍后重新派发
- **派发时（QUEUED → STARTING）再校验一次 snapshot 是否仍然有效**，而不只是批准时校验。远端也会在执行前校验 hash 和 commit

### 6. 取消请求发不出去

用户点了取消，但网络断了，cancel 请求到不了远端。

**处理：** 本地不等确认，直接产出 cancelled（reason 注明 unconfirmed）。远端因为没人订阅，租约到期后自己会停。

### 7. 节点自身崩溃

AgentServer 进程被强杀时，它拉起的子进程（POSIX 上是独立进程组）不会跟着死，成为孤儿。

**处理：**
- Orchestrator 重连时拿到 404 → FAILED(remote_lost)
- 节点启动时根据 pid 文件清理上次残留的进程 —— **骨架里还没做**，列入 D-09

### 8. 数据库写入卡住，导致误判断线

如果 Orchestrator 读事件流和写 SQLite 在同一条路径上，单写者队列一卡，就不读 socket 了，心跳也读不到，于是被误判为断线。

**处理：** 读网络和写数据库解耦。读到的事件先进内存队列，再由写库队列批量落库。心跳检测只看网络层有没有收到字节。

### 9. 跨机器比较时间

两台机器的时钟不一定一致。

**处理：** 每个超时只在一侧计算。执行超时（idle / total）由节点负责，因为它离进程最近；连接超时由 Orchestrator 负责。永远不要拿远端的时间戳和本地时间做比较。

## 安全

AgentServer 本质上是一个"收到网络请求就在本机跑命令"的服务，安全边界必须放在节点本地：

- **请求里不能携带命令。** 只能选节点配置文件里预先写好的 `profileId`。schema 用 `.strict()`，多出来的字段（比如 `command`）直接 400。已测试
- Token：至少 32 字符，按节点区分，用 `timingSafeEqual` 比较摘要
- 默认只监听 `127.0.0.1`，开放到局域网要显式配置。**明文 HTTP 在局域网里 token 和 prompt 都能被嗅探**，正式使用要加 TLS 或者走 WireGuard / Tailscale 隧道
- 子进程只拿到白名单里的环境变量
- 执行前节点重新计算 prompt hash；profile 开启 `verifyCommit` 时，校验工作目录 HEAD 一致且没有未提交修改
- **只读不是协议能保证的。** "Reviewer 只读"要靠节点操作系统层面实现：用没有写权限的用户运行 CLI，或者用只读挂载的 worktree。协议层只负责不把写权限交出去

## 预留手机 App

- 手机 App 是**控制面的另一个客户端**，和桌面 renderer 地位相同，只连 Orchestrator，**永远不直接连 AgentServer**
- `control-api.ts` 定义了与传输方式无关的命令、查询、事件。今天 renderer 通过 Electron IPC 使用，以后手机通过网络网关使用同一套格式
- 批准命令必须带 `expectedSnapshotHash`：手机上停留的旧页面如果对应的 prompt 已经变了，批准会被拒绝
- 客户端有权限范围（read / approve / permission / cancel），以后可以给手机只开部分权限
- **Phase 0 不需要做任何网关**，唯一的要求是 renderer 的 IPC 调用直接使用这套格式（已写进 C-02）

## 后果

- 正面：执行环境可以隔离；手机接入不需要改核心
- 负面：多了一个需要部署、升级、保护的进程；调试链路变长
- 风险：骨架里的 Windows 进程树终止、`.cmd` 启动、权限中继、孤儿清理都还没有实现或没有测试过（见 `apps/agent-server/README.md`）
