# 合批格子大小实测

问题：C酱 提议合并「E 港镇那 640 个 MeshToonMaterial × BufferGeometry」。

## 调查结果：那些网格已经是合批产物

- `src/station.js:118` 调的 `batchStatic` 来自 **`upstream/sakuragaoka/src/core/batch2.js`**（v2 合批：顶点色合并材质 + 贴图打图集 + 近场 48 m / 远景 200 m 格子）。
- 全场景 831 个 MeshToonMaterial 网格里，**606 个的父级就是 `static-batched`** —— 它们是合批输出，不是待合并的零散网格。
- 所以再合并它们 = 改合批格子大小，不是"把 640 个网格合成 1 个"。

## 本分支做了什么

只把合批参数暴露成 URL 可调，默认行为完全不变：

```
?nearCell=48&farCell=200&farR=150   （默认值即现在的行为）
```

## 实测曲线（E 港镇，冻结时钟 + grade=off）

| nearCell | 调用数 | 三角面 |
|---|---|---|
| 48（默认） | 1536 | 8,252,589 |
| 64 | 1451 | 8,278,406 |
| 96 | 1378 | 8,357,266 |
| 128 | 1354 | 8,379,117 |
| 200 | 1349 | 8,379,117 |

格子放大 4 倍，调用只降 **12%**（1536 → 1349），三角面 +1.5%。

## 画面不是逐像素一致

cell48 vs cell200 在同一 commit、冻结时钟下：

| 机位 | 变化率 | 最大通道差 |
|---|---|---|
| A 主街 | 0.160% | 103 |
| B 便利店 | 0.031% | 75 |
| C 后巷 | 0.134% | 146 |
| D 洗衣店 | 1.380% | 165 |
| G 铁路 | 0.006% | 17 |
| E / F / H | 0.000% | 0 |

合批改变绘制顺序，会影响半透明/描边遮罩的混合结果。

## 帧时

cell=48 三轮中位见 `cell48-timing.txt`（GPU 每帧合计 P95）。

**cell=200 的计时跑两次都超时没有产出**（探针在 180 s 看门狗内没跑完 8 个机位），所以给不出可信的 200 m 帧时。这一点本身说明把格子推大之后代价不明。

## 建议

不建议动合批格子大小：12% 的调用下降换来非零画面差异 + 计时都跑不完的风险。真正的杠杆在别处（材质数量、超大单网格如 houses 10.8 万顶点、以及 E 港镇的 ShaderMaterial 那 309 万三角面）。
