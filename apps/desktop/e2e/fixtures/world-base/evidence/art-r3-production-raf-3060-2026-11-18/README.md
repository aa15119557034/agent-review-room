# R3 主街与步行帧时归因

R3 原交件 `47a5c12e` 的生产帧在 `src/main.js` 中依次执行站区更新、行走控制、岛屿更新、`look.render`，然后更新 HUD 并约定下一次 RAF。分段诊断在正常加载后安装，以两个全新的 Electron 进程先后运行同一源码。两次都保留原生画质、傍晚实时游戏时钟、相同 A–D 按钮和真实 W 输入。

## 既有 11,602 帧

原交件首轮 A 的 546 个间隔中有 112 个超过 20 ms，其中 111 个位于 29–32 ms。长帧遍布约 10 秒，快慢帧的提交数和三角数中位数都为 1,592 次、8,009,684 个。复测原交件时，A 的 567 帧中有 90 个超过 20 ms，其中 88 个位于 29–32 ms，最长连发 28 帧。慢帧集中在第 7–9 秒，慢帧的中位提交量反而较低。其余镜头、候选与步行的同口径数据在 existing-intervals.json。

## 生产回调与 GPU 查询

对照只注册被动 RAF 观察者，读取场景现有的计数。诊断每四个生产帧选一个记录实际回调入口和出口，并分别计时四个原方法。相邻采样块改变抽样位置。每两个被选中的生产帧中有一个在 `look.render` 外围使用 GPU 时间查询。使用 QUERY_RESULT_AVAILABLE 后才读取结果，全程 369 次查询均完成，0 次 disjoint。两次采集的每个被动 RAF 均核实已看见同一时间戳的真实生产更新。

A 在对照和稀疏诊断的 10 秒内分别有 30/625 和 32/624 个长间隔，恰好分布在 5% 分界两侧。稀疏诊断捕获其中 7 个长间隔。对应生产回调实际执行中位 19.4 ms，其中 `look.render` 为 18.6 ms，回调结束至下次生产回调实际开始的间隙为 0.2 ms。有 3 个长间隔同时采到了 GPU 时间，中位 14.66 ms，范围 13.56–15.45 ms。A 所有样本里站区更新与岛屿更新中位仅为 0.3 和 0.2 ms。A 中以 GPU 查询采样和仅 CPU 采样的两组 `look.render` 墙钟中位都为 13.9 ms。

两个不同的时钟解释了为何这里不能把约 30.8 ms 直接分摊给 GPU 或呈现。A 长间隔对应的生产回调进入时，浏览器给出的本次 RAF 时间戳已过去中位 14.7 ms。到下一次实际回调入口只经过中位 19.6 ms，而浏览器给出的相邻 RAF 时间戳可相差约 30.8 ms。`look.render` 是主线程视角的调用墙钟，含 JavaScript 和同步的驱动工作或背压；GPU 时间是 GPU 命令区间的时长，两者可以重叠。当前没有硬件实际呈现的时间戳，也不能进一步把 `look.render` 拆成纯 JS 和驱动等待。

步行的两次独立运行差别明显。完整系统 CPU 与系统前台监视在对照期间提早结束，六段均没有对应样本。两次 NVIDIA 设备时钟与占用都有记录，稀疏诊断的主机 CPU 数据完整。当前没有足够证据将两次绝对 FPS 的差异完全归因于插桩或电脑上的其他活动。

## 复核

在本目录运行 `node verify.cjs`，可独立重算新采集的生产回调分段与 GPU 分位数，并从 existing 目录的四份原始压缩包复算既有 11,602 帧的分布和连续长帧。两套数据都核对 SHA-256。phase-summary.json 给出各段的分位数、系统采样覆盖、GPU 查询有效性和慢帧数量。instrument-page.cjs 是实际注入的测量代码。
